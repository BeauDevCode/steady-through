# Quick support and one next action

## Intent and choices

Continue the user's authorized free, private, beautiful cross-platform app. They accepted the next increment: trusted people inside Help, editing saved people, and direct access to Home's next action. The user delegated choices and opted out of repeated approval questions. Builder chooses existing Flutter/theme/vault and a1.5.0+9 preview, without changing schema4, encryption, sensing, thresholds or dependencies.

For support, considered a link-only Help→People route (more navigation), duplicated Help cards (drifting behavior), and shared person cards plus a full People route (chosen). For next actions, considered scrolling a lazily built five-stage Path (fragile target realization), a separate task system (unnecessary), and an ephemeral focused route for the existing action (chosen). The full Path remains available; no new persisted task type.

## Product behavior

- Help keeps its existing immediate-danger/crisis/local-service content and Back behavior, and adds **Your trusted people** before More support. Preview up to3 saved people in stored order, without ranking or inferring relationships. Show **View all saved people** for the full People route, and an explicit Add person empty state. The shared card exposes saved name/optional number and explicit Call/Text/Copy actions; no automatic launch, call, message, clipboard write or permission request occurs. Phone handoff is not a delivery guarantee; unavailable handlers leave the number visible with a copy fallback. Existing crisis content/numbers are unchanged.
- All shell Help entries and standalone tool Help fallbacks receive the current controller. Help opened from breathing still pauses it; return reaches the original route. Full People management reached from Help has Back to Help. No contact permission, cloud service, source opt-in or active event is required.
- People gains **Edit person** using prefilled name/optional phone and Save/Cancel. Trim text, reject blank names, allow clearing a phone, preserve ID/order/other records. Use the same Add/Edit form from both surfaces; retain confirmed removal. Save failure keeps form input and permits retry; disable duplicate submissions but keep Cancel available. Backgrounding invalidates the dialog until closed/reopened, preventing resubmission after an already-started save. All records remain encrypted; editing/removing requests known residual-copy cleanup, preserving committed-save warnings versus primary failures and external-export limits.
- Home's pending action gains **Go to this step**. A focused **Your next step** route shows its event and exact action, explicit Mark step done/Undo completion, Back to Home, Help now and View full path. Full Path access remains for no-action, all-done and completed-event states. No completion on navigation and no automatic advancement to another action.
- The focus target captures event ID, action ID and document-replacement revision. Render current data for that target, never a stale copied plan. Removed actions, completed events, changed active events or replaced documents show an explanatory unavailable state and a way back/current Path; they cannot mutate another action or an imported same-ID record. A successful completion reflects persisted data; primary failure leaves it unchanged with retry. Concurrent unrelated writes survive.
- Use the existing calm palette, wrapping48px controls, Simple words, keyboard actions/live feedback,320px/200% text and reduced motion. Do not add animation-dependent navigation or scroll-to-target assumptions. Keep the whole app free and usable with all learning sources off. People/contact data never become learning examples or features.

## Data and lifecycle contracts

Schema remains4/read validated1..4. AppData, TrustedPerson and PlanAction already carry the needed fields. No birth date/contact permission or new persisted derived state. Imported native-source consent reset, private ratings and old plans remain intact.

Controller APIs operate on current data inside the write queue:
- `addPerson(name,phone,{int? expectedRevision,bool Function()? isActive})`; existing callers remain compatible.
- `updatePerson(id,name,phone,{required TrustedPerson expected,required int expectedRevision,bool Function()? isActive})`.
- `deletePerson(id,{TrustedPerson? expected,int? expectedRevision,bool Function()? isActive})`; UI supplies both expected record and revision.
- `setFocusedActionDone(eventId,actionId,done,{required PlanAction expected,required int expectedRevision,bool Function()? isActive})`.
New/guarded ownership mutations reject disposed controllers, replaced documents, failed active guards, and mismatched expected ID/instance. Focus additionally requires the same current active, unfinished event. Corrections/removal purge known residual copies; normal action completion does not change retention policy. A queued canceled/background/stale action is rejected before save; an already-started atomic save may finish without navigating/popping a different route. No whole copied list is submitted by UI.

Shared `ViewActivity` observes foreground/epoch/alive state for the new views; existing feedback policy stays untouched. Contact handoffs recheck the visible expected record/revision before launching, suppress duplicate pending actions, catch both false returns and thrown failures, and do not display late success over another view. Clipboard errors are reported. Generic opted-in tap counters may still count ordinary UI taps; chosen people/phone values are not learning inputs.

Interfaces: `PhoneActions`/`UrlLauncherPhoneActions` move to `features/people/phone_actions.dart` and remain exported from PeopleScreen for compatibility. `PersonCard(controller,person,{phoneActions,showManagement=true})` and `PersonFormDialog(controller,{person})`; `showPersonForm` wrapper. `TrustedPeopleSection(controller,{phoneActions})` owns Help's preview and full-People route. `HelpScreen({simpleWords=false,AppController? controller,phoneActions})` and `HelpNowButton(...,AppController? controller)` retain controller-free general help compatibility. `NextActionTarget(eventId,actionId,replacementRevision)` in `model/next_action_target.dart`; `FocusedActionScreen(controller,target,{onOpenHelp,onOpenPath})`. Home adds optional `ValueChanged<NextActionTarget>? onOpenNextAction`; shell supplies navigation and all Help controllers.
