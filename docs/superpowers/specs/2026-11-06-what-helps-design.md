# What helps you: optional tool ratings

## Intent and approach

Continue the user's authorized free, private, cross-platform support app. The next complete increment connects support tools to what the person explicitly found useful. The user delegated implementation choices and requested continued work without repeated approval. Keep Flutter, the local encrypted vault and the calm visual system.

Considered: one latest preference per tool (small but loses the person's history); an outcome/ranking model (needs a separately consented effectiveness study); a bounded personal rating history with transparent retrieval (chosen by builder). Store explicit ratings and show their meaning directly; no efficacy score, symptom prediction, automatic intervention, notifications, quotas or new permissions. A tool's latest retained answer determines whether it can appear as a recent helpful idea; every tool stays available in its normal place.

## Evidence

Checked 2026-11-06. These inform design, not proof of clinical benefit.

- [HeartSteps original micro-randomized trial](https://pmc.ncbi.nlm.nih.gov/articles/PMC6401341/) used repeated randomization and a prespecified step-count outcome. A usefulness answer alone cannot establish a causal benefit. This app records personal opinions, not treatment effectiveness.
- [Primary study of assessment non-response](https://pmc.ncbi.nlm.nih.gov/articles/PMC11759496/) found contextual differences in responding in its smartwatch setting. Our inference: skip, stopping and silence remain unknown and never count as negative ratings or failed use.
- [W3C interruption guidance](https://www.w3.org/WAI/WCAG21/Understanding/interruptions.html) supports suppressible nonessential interruptions. Our inference: quiet collapsed prompts at stopping points, visible Skip and a setting to hide prompts; no exit interception.
- Existing [private-learning research/design](2026-11-06-saved-moments-design.md) remains applicable. Tool ratings do not become feeling labels or sensor-model inputs.

## Product behavior

1. A collapsed **Rate this tool (optional)** affordance appears at Grounding's finished view, after Breathing's explicit **Done for now**, and at the Path game's Finish view. Opening it presents **Helpful / Not this time / Skip**, with brief local encrypted-storage copy. Closing a tool, help, skipping, reaching Finish or any other action alone saves nothing. Stop/Back/Help keep their current immediate behavior. Grounding can reach the ending through skips; never claim every exercise step was performed. Game feeling and usefulness are independent optional answers.
2. Helpful/Not this time saves one guarded record. Disable rating mutations while saving, allow navigation/help, show success only after persistence. A failed write retains the choice and offers retry without duplicates. A saved answer can be changed in place or undone using its exact receipt during that prompt. A prompt's Skip writes nothing and does not delete earlier answers. A new breathing attempt/game board has fresh prompt UI. An old async save cannot mark a different attempt as saved.
3. Breathing gains **Done for now** only after Start; it cancels the pace and reveals the optional feedback. Start again begins a new attempt. Pause and Help do not finish, rate or auto-resume. Pause on leaving the foreground. Respect reduced motion with a static circle and usable pace text, not zero-duration layout animation.
4. Tools gains **What helps you** with descriptive counts for each rated tool and the latest answer. **A tool to revisit** uses the most recent Helpful answer only among tools whose latest retained answer is Helpful. Explain the date/reason and open only after a tap. No proportions, leaderboard, inferred emotion, effectiveness claim, minimum rating target or hiding/reordering ordinary tools. A negative answer does not remove access.
5. A full **Your tool ratings** view shows all retained entries newest first with local dates, tool and answer. It supports Add a rating (manual opinion even after stopping early), per-record change/delete and confirmed Clear ratings. Corrections preserve ID/time/tool; deletes target exact unchanged records. Clear removes ratings only, preserving prompt/suggestion settings, events, feeling learning and game history. Separate settings **Show optional ratings after tools** and **Use my ratings for ideas** default true, act only on this feature, and persist. Sources off/learning paused do not restrict rating ownership or tools. Hidden prompts do not block manual rating/history management.
6. Current possible-vehicle motion suppresses feedback and rating mutation controls; Help/Back remain reachable. Use only the existing optional session's `snapshot.possibleVehicle` safety flag, never train/invoke the feeling model for ratings. No new source or grant is requested. Missing motion stays unknown; this is not a driving detector guarantee.
7. Every UI write captures document replacement revision and an alive/foreground/attempt guard. Check both inside the serialized mutation before a repository write begins. Import/clear-all, backgrounding, a replaced board or disposed prompt must reject a stale queued action. An already-started atomic save may finish, with no late success shown on another route. A stale history dialog cannot edit an imported same-ID record. Failed undo retains its receipt; deleting or changing the target invalidates it. Closed controllers reject new feedback writes.

## Data and privacy

- App version **1.4.0+8**, write **schema4**; validated versions1/2/3 migrate with empty ratings/default settings. Read1/2/3/4. Existing event guidance rules apply for version>=3, preserving guide/actions/check-ins/theme/reading style/learning. Schema4 requires exactly one new top-level `toolFeedback` object. A schema1/2/3 document containing that field is rejected. Apps that read only up to3 cannot read new4 vaults/exports; document upgrade/backup boundaries.
- `SupportTool { grounding, breathing, pathGame }`, `ToolRating { helpful, notThisTime }`, immutable `ToolFeedback { id, createdAt, tool, rating }`. ID1..200 characters/nonblank; strict enum/object keys and timestamp validation. Normalize constructed timestamps to UTC; new-format JSON timestamps require Z or explicit valid offset. No event linkage, completion state, durations, feeling labels, notes, game moves or sensor readings.
- `ToolFeedbackData { showPrompts=true, useSuggestions=true, ratings=[] }`, strict booleans, unique IDs, immutable list, maximum1,000 records. Inclusive180-day cutoff, future entries excluded, deterministic `(createdAt,id)` ordering, retain latest1,000. Bound a1,001-record candidate before constructing a constrained object. Imported over-cap lists fail validation before confirmation.
- All records/settings live in the existing encrypted AppData document and independent encrypted export. No plaintext cache/database/server. Keep encryption envelope, KDF and native adapters unchanged. Prune both feedback and feeling learning at unlock, export and every committed mutation. Removed IDs from old/candidate data trigger residual cleanup; corrections explicitly request it. Committed-save cleanup warnings remain distinct from primary-save failures. External exports remain outside local deletion control.
- Tool ratings never change a learning source, LearningExample, calibration or GameRound. Clear learning/game history preserve tool ratings; Clear all resets them with the rest of the document. Imported ratings/settings are retained, while the existing native-source consent reset remains.

## Architecture / builder-owned details

Use a focused model/summary, current-state controller APIs, a small foreground/attempt guard owned by feedback widgets, reusable prompt/history components and an optional safety-session parameter carried through all existing tool entry points (Tools, Home, Insights and game grounding). Do not create a generic analytics platform. Keep full history lazy, controls at least48 logical pixels, wrapped actions, keyboard dialogs, live action/error semantics, standard/Simple words,200% text and reduced motion. Existing palette/typography remain.

Controller interfaces: `recordToolFeedback(tool,rating,{required int expectedRevision,bool Function()? isActive}) -> Future<ToolFeedback>`; `correctToolFeedback(id,rating,{required ToolFeedback expected,required int expectedRevision,bool Function()? isActive})`; matching delete; clear and settings updates with revision/guard; `pruneRetainedData()`. Save returns the instance captured inside the successful mutation, not a lookup after awaiting. This guard is production lifecycle policy, not test-only API.
