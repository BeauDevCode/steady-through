# Recovery help and iPhone Release preparation

The next preview closes two concrete gaps in the existing app: forgotten-passphrase help currently leads straight to a destructive confirmation, and iOS packages currently target the Simulator only. Continue the existing Flutter app, free/offline core, local encryption and optional learning. The user has delegated implementation choices and asked for continuous work; these choices are the builder's decisions, not new user approvals.

## Approaches and decisions

- For recovery, a short non-destructive help dialog fits the existing vault gate. A new welcome wizard would duplicate the clear first-event flow. Direct restore behind a locked vault would require new key/storage replacement behavior and is deferred. Choose help before the existing reset confirmation.
- For iPhone preparation, add an isolated unsigned Release app build targeting iPhoneOS. A Simulator binary is not sufficient even when it is arm64. An Xcode archive is possible but adds a second packaging format before signing is available; choose one complete Runner.app ZIP for compilation evidence. It is unsigned, not installable and not physically validated.
- Reuse the clean checkout on a codex branch, existing SDK/dependencies/theme and independent source review. Local Xcode is now available, but zero valid signing identities were found. Do not configure an account, accept terms, spend money, grant permissions or handle private keys.

## Recovery behavior

The existing locked-only help/reset link becomes `Forgot your passphrase?`. Its first action opens `Help with your passphrase`, a scrollable, constrained, accessible dialog. Default `Back to unlock` dismisses without changing records, text entry, busy state or callbacks. `Start over…` explicitly continues to the existing typed-DELETE reset confirmation; it never deletes directly. Keep all reset/open serialization, validation and cleanup behavior unchanged.

Explain in plain, bundled text: there is no account/server recovery; check a safely stored passphrase copy; exported .steady backups have the separately chosen export passphrase; if a vault can be opened, restore via More → Settings → Import data with replacement confirmation; if the current vault remains locked, check an existing backup and its passphrase on another installation before discarding it. Do not imply a backup exists, that the app can recover a lost key, or that the export passphrase unlocks the current vault. Keep the locked vault until the person knows their backup opens. Without the vault passphrase or a usable backup, its records cannot be recovered.

This dialog reads no vault, discovers no backup, opens no file picker and adds no text fields or learning event. Hide it when no reset callback exists; disable it while submitting. Use the existing palette/typography and safe primary dismissal. Check 320px/200% text, keyboard/back/escape and dismissal. Native smoke test names and assertions remain unchanged.

Adhoc vendor signatures do not establish app distribution signing. No provisioning profile is supplied.
