# 1.2.1 implementation and release decisions

The release tag is the exact tested source `0f62db5ee2ba0e0769273de5872b1214ea6bafc5`; [run42270965635](https://github.com/BeauDevCode/steady-through/actions/runs/42270965635) passed all seven jobs. Later publication records on main change documentation only. The following controller rulings are preserved in their original order; the [quality record](../quality-status.md) contains observed results and remaining manual/distribution work.

1. **Fix the new CI job, archive and evidence names before implementation.** This lets release staging require the exact intended package and four allowlisted device evidence files while preserving the six existing jobs. A mistaken name costs a routine rename/rebuild; it does not justify weakening an existing gate.
2. **Keep the Mach-O parser's role to bounded compilation/platform metadata.** Fresh controlled production builds and every actual slice's device-platform proof are required. The helper does not deeply audit unrelated segment/symbol/signature payload semantics or claim a general loader/security audit. If that scope proves insufficient, further validator hardening is needed; no distribution-security certification is implied.
3. **Fix the prohibited-empty-directory omission before publication.** Review identified a direct rejected-path contract gap even though executable payloads were already rejected. The same path policy now applies to all entries, with semantic directory/ZIP regressions. The cost was a small focused fix/test/review round, with no broader parser or app-data change.
4. **Review source before publication, then close release evidence after observation.** Scoped reviews and the whole-branch review precede external release actions; runtime/artifact/publication outcomes remain explicit gates rather than advance claims. If the ordering needs adjustment, documentation/evidence follow-up may be required; no publication gate is skipped.
5. **Tag the exact final CI source.** The release tag and package source are identical, rather than relying on a code-equivalence claim for the tag. Publication evidence is recorded separately on main. The consequence is that the immutable source snapshot still contains its pre-build pending documentation; latest main, BUILD-INFO and release notes contain the observed outcomes.
6. **Verify a documentation-only main successor explicitly.** The intended live main SHA must match, the tested source must be its ancestor, and `git diff --no-renames --name-only -z` must show only allowed documentation paths. Publication records use `[skip ci]` to avoid rebuilding identical software solely for documentation. Incorrect equivalence could otherwise leave untested code on main, so any non-documentation change fails verification. This refines the initial exact-main/tag requirement without weakening the exact tested tag/package binding.

The later observed Simulator banner defect received tests first, a minimal same-UUID format fix and a scoped review. Failed, unknown and unready states still reject, and the corrected source received a fresh complete seven-job run. The failed earlier candidate is retained as diagnostic history, not release validation.
