# Contributing to Steady Through

Thank you for helping make Steady Through clearer and more reliable. Keep changes small enough to review and explain the behavior they change.

## Development checks

Use Flutter **3.47.9** and the native toolchain for the platform you are testing. From the repository root:

```sh
flutter pub get
dart format --output=none --set-exit-if-changed lib test integration_test tool
flutter analyze
flutter test
```

On a host with the Android SDK, also run `./gradlew :app:testReleaseUnitTest` from `android/` when changing motion classification or session state. CI retains the JUnit XML as `android-motion-unit-results`; check the actual test count and failure/skip counts.

Build on the relevant host with the commands in [README.md](README.md). The GitHub Actions workflow is configured for seven jobs: shared checks, the five original production/native targets and a separate unsigned iPhoneOS Release build/validator; its artifacts are development outputs, not signed store releases. Check the actual run for the revision being reviewed. Note the exact platform and whether you ran on a device, simulator, or only compiled. Do not mark a native source validated on a device based on a successful build, mocked platform channel or previous release alone. Record current evidence and remaining gaps in [quality status](docs/quality-status.md).

For reduced motion, render static content instead of a zero-duration `AnimatedSize`. Flutter can synchronously notify its size controller during layout when the child changes size. Keep the guide and Insights save/pause/resize/disposal regressions passing; preserve normal transitions when motion is enabled. Mobile native CI uses verbose Flutter launch logging for diagnosis and still requires the same three verified application cases.

## Native smoke checks

The `integration_test/native_smoke_test.dart` suite is separate from the fast `flutter test` unit/widget suite. Run it on a native target, then check its JSON-lines report. For example, on macOS:

```sh
mkdir -p build
flutter test integration_test/native_smoke_test.dart -d macos --reporter expanded --file-reporter json:build/native-macos-results.json --timeout 5m
python3 tool/ci/verify_native_results.py build/native-macos-results.json
```

Use an Android emulator ID, an available iPhone simulator ID, `macos`, `windows`, or `linux` for `-d`, and give each target a distinct `build/native-<platform>-results.json` report. On Linux, run Flutter under `xvfb-run -a`; on Windows, create `build` with PowerShell's `New-Item -ItemType Directory -Force build` and invoke the verifier with `python`. CI uses `tool/ci/prepare_ios_simulator.py` to choose and foreground an available iPhone simulator from `simctl` JSON; it needs `GITHUB_ENV` in the runner. Run `python -m unittest discover -s tool/ci -p 'test_*.py'` to check the simulator-selection, native-report, Mach-O and unsigned-device bundle/archive helpers themselves.

The verifier requires these three named application tests in **each** native report: `native bridge remains paused without source consent`, `native vault keeps an event through lock and authenticated unlock`, and `native encrypted backup restores only after its own passphrase`. It rejects a missing or duplicate required test, skipped/failed tests, runner errors, unfinished tests, or a missing successful final event. Reporter loading/teardown events may also appear; do not treat those as application test passes. Preserve the report and console log on failure. A build artifact or a test process exit code alone is insufficient evidence that the three cases executed.

Native fixtures use fictional records and uniquely created temporary directories. The suite uses the real `VaultGate`, `VaultStore`, KDF, codec and filesystem repository; it asks `path_provider` for a native temporary path only to check plugin registration. Successful fixtures are cleaned up only after their app/session is closed. A failed or timed-out UI fixture may be left in its owned temporary directory for diagnosis; tests must never touch a person's normal app records. The encrypted import/export case calls `DataPortability` with a test-owned file gateway and scripted passphrase/confirmation callbacks. Actual encryption, file bytes, validation, replacement behavior and repository persistence remain exercised; the OS chooser and Settings passphrase/confirmation dialogs are outside that native case. Every optional learning source stays off, and the suite requests no OS grant or physical sensor reading.

The third native case creates a caregiving event with two selected steps, edits and completes one, adds a custom step, and keeps dark/Simple words settings. It compares complete event JSON after independent-passphrase import and after authenticated disk reopen. Keep all three exact test names, the real KDF and file gateway, and sources off. The separate encrypted portability unit test uses synthetic all-source choices without constructing a collector to establish that import retains manual/in-app choices while resetting native sources and owner confirmation. Do not claim the native sources-off fixture establishes enabled-source consent reset.

For reproducible guidance images, run `flutter test --update-goldens tool/capture_guidance_ui_test.dart`. It uses actual creation, guide chooser, starter picker, Path and Home UI with bundled fonts and fictional data. Four profiles cover standard/light mobile, Simple/dark mobile, 320px Simple/light at 200% text, and 1440px standard/dark desktop. Inspect every generated `docs/screenshots/guidance-*.png`; a successful render alone does not establish useful layouts or native accessibility. The capture builds no learning session and uses no passphrase, vault or permission grant.

For recovery images, run `flutter test --no-pub --concurrency=1 --update-goldens tool/capture_recovery_ui_test.dart` and inspect all 11 `docs/screenshots/recovery-*.png` images from its four profiles, including 320px/200% text with scrolled controls/help and keyboard inset. The fixture uses real locked/help UI with empty fields, no disk vault, learning session, grant, backup discovery or reset. Recovery changes must preserve help dismissal and **Back to unlock** without storage operations; only **Start over…** may delegate to the existing typed-`DELETE` reset path. Never reset a real vault to capture this flow.

The [iOS distribution guide](docs/ios-distribution.md) gives the production unsigned-device build and directory/archive verification commands. Preserve the prior directory report and verify the archive against it before staging; require platform 2/iOS for every Mach-O slice, not just arm64. Keep Simulator platform/runtime validation independent. Production packages must be archived before any integration-test recompilation. The unsigned device job does not execute the native suite or produce an installable IPA; Apple signing/provisioning and physical iPhone checks remain separate owner-controlled work.

CI is configured to run this suite on an Android emulator, an iOS simulator, macOS and Windows hosts, and Linux under Xvfb, with per-target JSON/log artifacts and report verification. Native-channel registration and paused/unsupported behavior can be checked there. This does not establish behavior with real Usage Access or motion permission grants, physical sensors, phone/SMS handlers, OS file dialogs, screen readers or actual users. Record those separately on physical devices or appropriate native hosts before making broader source or accessibility claims.

Use the [manual device-validation guide](docs/device-validation.md) for the physical-device and native usability checks outside this suite. Record an outcome for each platform/build; the guide itself is not evidence that a check passed.

## Changes that need particular care

- Keep context voluntary and per event. The five guides share the existing five journey stages and include standard/Simple words content. Preserve saved action IDs, order, wording and done states when guide, reading style or catalog copy changes. Validate stable starter IDs inside the serialized mutation queue; reject unknown, repeated and cross-guide IDs without partial writes. Guide metadata and event text never become learning inputs; explicitly enabled in-app aggregate counters may include ordinary UI taps. Cite guidance sources in [the content note](docs/guidance-content.md) without claiming endorsement, diagnosis or age-wide effectiveness.
- Preserve the version boundary: write version 3; read validated versions 1/2/3, assigning General to legacy events and retaining their actions. Older apps cannot read new version 3 documents. Reject invalid version 3 context before import confirmation or replacement. Do not silently downgrade data or bypass authenticated encryption.

- Keep the whole app free and usable offline without accounts, analytics, advertising, cloud emotion services or personal-data transmission. Every learning source starts off in a new vault. Imports may restore manual/in-app choices, while system usage and motion sources reset off. Device permissions must stay optional; planning, tools, people and help remain available if all sources or permissions are declined. Do not add permissions or data collection without explaining the need and updating [PRIVACY.md](PRIVACY.md).
- Treat game moves as observable actions within a game. Do not claim they measure stress, diagnose a condition, or support a clinical score. Ask the player how a round felt before tailoring a suggestion. Avoid saving raw tap traces.
- Keep Help now reachable during tools and game play. Label 988 as a U.S. option and direct people elsewhere to local services. Keep Stop visible on exercises and Skip visible in grounding. Do not require breath holding, closed eyes, or rapid/deep breathing.
- Preserve import safety: authenticate encrypted `.steady` files or validate complete legacy JSON before asking to replace local data. Invalid, unauthenticated or cancelled imports must leave existing data untouched. New exports are encrypted and use their own chosen passphrase. Imported device-owner confirmation must not activate system sources on the current device; preserve history but require fresh opt-in for usage and motion. Confirm full replacement, vault reset, delete-all, learning clearing and game-history clearing.
- Test large text, screen readers, keyboard focus, narrow layouts, light/dark appearance, and phone/SMS fallback where the platform has no handler. [W3C mobile accessibility guidance](https://www.w3.org/TR/wcag2mobile-22/) is a useful review reference.
- Use original copy and cite authoritative sources for health, crisis, privacy, or platform claims. The [WHO stress guide](https://www.who.int/thailand/activities/doing-what-matters-in-times-of-stress), [NIMH help guidance](https://www.nimh.nih.gov/health/publications/my-mental-health-do-i-need-help), and [988 Lifeline](https://988lifeline.org/get-help/) inform the current content; they do not endorse this app.

## Vault and consent boundaries

All durable app records and settings belong in the authenticated encrypted vault, including recovery/staging copies, learning labels and calibration parameters. Use the existing AES-256-GCM codec and bounded envelope parsing. Keep random salts, fresh per-save nonces, authenticated format metadata and the PBKDF2-HMAC-SHA256 work factor intact. Derive keys outside the UI isolate. Never add a plaintext fallback, save a passphrase, silently reset a damaged vault or log decrypted records. Closing a key object is not proof that every runtime or OS memory copy was erased.

Tests for storage changes should expose wrong-passphrase and tampering failures, independent export passphrases, nonce changes, interrupted saves, authenticated recovery, permission/storage errors and bounded untrusted metadata. Legacy migration must authenticate and read back its encrypted document before removing known plaintext primary/backup/temporary files. A pre-commit validation, authentication or write failure must reject the change and preserve the prior active records. Once an active-vault save commits, a later failure to purge known older copies must leave the operation successful, show a retryable cleanup warning, and avoid inviting a duplicate form submission. Ordinary saves must not silently dismiss that warning; only a confirmed successful purge clears it. Clear learning and Delete all remove records from the active vault and attempt to purge known recovery/legacy copies. If that purge fails, report the committed change and warn that earlier copies may still contain removed data. Exports and OS backups are outside app deletion controls.

Keep in-app consent separate from OS permission and support detection. Enabling a system source requires device-owner confirmation, with any system grant requested only by a separate explicit action. A supported source without a grant is missing evidence. An enabled source that becomes unsupported must still be individually revocable. Turning off a source, user pause, backgrounding or locking must stop its collector and invalidate late callbacks/readings. An unlock finishing in the background must not uncover records or start collectors. Resume must preserve a user's deliberate pause.

On iOS, keep Core Motion manager construction and instance operations out of passive bridge registration, paused reads and stops before an opted-in session exists. The no-consent native flow must complete without accepting or dismissing a Motion & Fitness prompt; such an interruption is a consent regression. Create a manager only for the separate explicit permission action or after the active, opted-in and OS-authorized session guards pass.

Only whitelisted aggregate counts, durations and uncertain vehicle context cross a native channel. Never send or persist app/package names, window titles, typed content, screenshots, raw key/touch traces, location or routes. Android may use package identifiers transiently to deduplicate UsageStats events; those identifiers must remain inside the native function. Use exact event windows rather than treating an expanded daily UsageStats bucket as the last hour. Preserve null for unsupported, denied, invalid and absent readings. Windows/Linux system sources and iOS cross-app usage remain unavailable until separately implemented and verified; do not bypass Apple's entitlement or extension requirements.

Possible vehicle movement suppresses interactive reflection choices in Insights; help stays available. A label action with motion enabled must request a fresh native reading before it accepts the answer. It cannot establish who is driving. Follow each API's update contract: [Core Motion updates](https://developer.apple.com/documentation/coremotion/cmmotionactivitymanager/startactivityupdates(to:withhandler:)) are delivered on classification changes, so an arbitrary heartbeat timeout cannot establish that a known vehicle state ended. Unknown readings must not create a diagnosis, score or reassuring claim. Stop/unsubscribe, permission revocation, backgrounding and late callback races need native/device review as well as Dart tests.

## Personal model review

Train and evaluate only on explicit labels and consented, bounded aggregate features. Manual-only input can support a self-reported trend without a predictive claim. Personal matching currently needs 20 eligible examples over seven distinct UTC observation days, at least five examples of each of two concrete labels and at least two comparable features. Unsure does not become a concrete training class. Test missing data, one-class and sparse histories, overlap/contradiction, changed recent patterns, disabled features and corrections before changing these gates.

The 60-day calibration uses an earlier training set and a later held-out set with no shared observation day. Current coverage gates include at least 30 training examples over 14 observation days and at least 12 later examples over seven observation days, with class and comparable-feature coverage on both sides. A candidate must improve on the majority-label baseline and any incumbent before adoption. Keep the chronological split and coverage checks independent of candidate selection. Internal label-agreement checks do not justify publishing a clinical or real-world accuracy claim. Preserve the current revision if evidence or improvement is insufficient, and show the reason.

Retain at most 180 days or 1,000 learning examples, whichever limit is reached first. Enforce retention at storage/read boundaries and when labelling/reviewing, and keep old/future observations from creating a current confident match. Review all inference wording independently before publishing a preview. Follow the [private-learning specification](docs/superpowers/specs/2026-11-05-private-learning.md), while verifying it against the final code and actual platform behavior.

## Pull requests and issues

Include a short description, the reason for the change, commands run and their results, and any platform limitation. Add focused tests for behavior changes. Never commit signing credentials, tokens, passphrases, real user records, vault/recovery files, `.steady` or JSON exports, or private contact information. Use fictional sample data in issues, captures and tests. For a security or privacy concern, describe a minimal reproduction without exposing someone's data. Do not publish a preview until its current security/inference review and required native build checks have been recorded; physical source and accessibility validation remain separate evidence.
